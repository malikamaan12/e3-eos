# P00 authentication boundary — implementation slice

Updated 26 September 2026. This is implementation evidence for part of P00-ST04 and AT-003/AT-006, not P00 phase acceptance or production readiness.

## Implemented

- Protected tenant routes resolve opaque bearer/cookie sessions through PostgreSQL on each request. Identity, role, audience and Super Admin claims supplied by callers do not establish authority.
- A session must have a current, non-revoked organisation membership. An organisation selector is checked against the same database membership. Revoked Super Admin membership does not bypass this requirement.
- Session lookup failures fail closed with an unavailable response. An invalid session never falls back to synthetic identity headers.
- Verified identities replace legacy actor/role/organisation header values used by existing handlers. The separate operational-constraint guard uses the same credential parser and current-membership requirement.
- Canonical account auto-provisioning, canonical unconfigured credential activation and unrestricted UAT identity switching require an explicit local synthetic opt-in. Ordinary invited/seeded accounts with established credentials continue to log in without it.
- Credentialed CORS uses an exact configured origin allowlist. Unsafe commands from an untrusted browser origin are rejected before controller dispatch, including login/logout; cookie-authenticated writes without Origin are also rejected. Non-browser commands use an opaque Bearer credential, which is still validated through the database. Incoming Host/Origin values never determine the allowlist.
- Controlled invitations can be listed, created and cancelled by a current internal Super Admin. Creation queues an encrypted delivery intent and returns its status; it does not send email or expose the token/link. Invitation creation, cancellation and acceptance commit their audit, outbox and durable idempotency receipt with the domain changes.

## Local synthetic opt-in

`EOS_ENABLE_LOCAL_SYNTHETIC_AUTH=true` is honoured only when `NODE_ENV` is `development` or `test` and `ENVIRONMENT` is `local`, `development` or `test`. Unset Node/environment names default to development/local. The flag defaults off; production, staging, preview and unrecognised environment names cannot enable it.

This opt-in permits header/pre-attached fixture identities **only without any supplied session credential**, and enables synthetic canonical setup/UAT switching. Use it exclusively with isolated synthetic local data. It is unnecessary for normal password login. It is not a recovery/bootstrap procedure for a deployed environment.

The session-boundary and local synthetic opt-in changes require no schema migration. The controlled invitation increment requires migration `0015_controlled_invitation_lifecycle.sql`. Existing server processes must be restarted after building. Seeded credentials already stored in the database remain credentials; these changes do not rotate them or certify them for deployment.

## Browser origin configuration

Set `EOS_WEB_ORIGINS` to comma-separated exact HTTP(S) origins, for example `https://eos.example.test,https://admin.example.test`. Alternatively a single `APP_BASE_URL` origin is used. Paths, credentials, wildcard entries and non-HTTP(S) values are rejected. Explicit configuration replaces the local defaults. Production/staging/preview do not implicitly trust localhost or their incoming Host header: configure the real frontend origin even for same-origin deployments.

Without explicit origin configuration, local/test environments permit `http://localhost:3000`, `:3001`, `:3002` and the corresponding `127.0.0.1` origins used by Vite. A deployed environment has an empty default allowlist. CLI/server clients may omit Origin when using Bearer authentication; cookie commands must send an allowed Origin. Cookies do not override a supplied Bearer credential.

## Controlled invitation boundary

`GET /invitations` returns the latest 100 records from the verified organisation. `POST /invitations` and `POST /invitations/{id}/cancel` require current internal Super Admin authority, a reason and a stable `Idempotency-Key` of 1–200 characters. The server rechecks authority inside the transaction. The allowed roles come from `/admin/access-capabilities`; `super_admin`, `executive` and existing platform administrators require separate governance and cannot use this flow. The server derives audience from role: `client_user` becomes `client`, and other supported roles become `internal`.

Creation requires a valid 32-byte base64 `EOS_INVITATION_DELIVERY_KEY`, an integer `EOS_INVITATION_TTL_HOURS` between 1 and 168 (default 24), and a valid `APP_BASE_URL` origin. Deployed environments require HTTPS; local/test environments can use HTTP and default to `http://localhost:3002` when no origin is configured. The database stores a SHA-256 token hash. The delivery outbox contains an AES-256-GCM encrypted token and fragment link, labelled with `EOS_INVITATION_DELIVERY_KEY_ID` (default `v1`). No sender is implemented: `queued` is a delivery-intent state, not evidence that email was sent or received. Cancellation invalidates the token and cancels any still-pending delivery intent.

`POST /auth/invitations/inspect` accepts the opaque token in its request body and returns limited invitation metadata without granting access. `POST /auth/accept-invite` requires that token and a stable command key. Both recheck the inviter's current internal Super Admin membership. Expired, cancelled, legacy unverified or stale-authority invitations fail closed. Existing-account acceptance additionally requires a real session for that exact account, including on retries; the invitation never changes an existing password or account name, or restores an existing revoked membership. A new identity supplies a password of at least eight characters and at most 72 UTF-8 bytes. New-account acceptance retries require the original password and normalized name payload; existing-account retries require the matching session. A consumed token under a different key is unavailable.

Acceptance creates the invited organisation membership only. It creates no project grant or login session. Invitation creation creates neither a user nor a membership. Legacy invitation records remain visible as `legacy_unverified` but are not eligible for acceptance; the legacy `POST /admin/users` invitation action remains unavailable. The invitation contracts were introduced at version 1.2.0 in both `contracts/CORE_COMMANDS.openapi.yaml` and `packages/contracts/CORE_COMMANDS.openapi.yaml`; the fifth project-module batch verified those mirrors at version 1.4.0.

The web client no longer authenticates canonical users locally when the server rejects or cannot verify sign-in. It restores user/role/organisation from a verified server session, including newly invited identities, instead of relying on the local canonical directory. Invitation links use fragment tokens; the acceptance screen removes token parameters from browser history immediately and keeps them only in memory. Reopening the delivered link is required after a page reload. In-page retries retain the command key; key persistence across browser reload is not implemented. A queued invitation does not certify project access checks in other controllers.

## Access administration batch — 26 September 2026

The new commands are POST /memberships/:id/role, POST /memberships/:id/restore and POST /project-access (plus :id/change and :id/revoke). They use current internal Super Admin authority, current organization scope, recorded reasons and stable idempotency keys. Changes to existing records require expectedVersion. The admin directory supplies membership rowVersion, and revocation increments it.

Role changes and restoration target ordinary memberships only. Self changes, privileged memberships (including global Super Admin users), privileged promotions and audience transitions are rejected. Both operations invalidate all of the target user's sessions across devices and organizations. Restoration revokes historical active project grants; a fresh sign-in and new explicit grant are necessary. Role changes retain project scope but project actions also require the current role permission.

Project access is recorded against a same-organization membership and project. There is no grant backfill and no owner or Super Admin shortcut for business project access. Internal memberships support viewer/editor; clients support viewer only and receive minimal identity/maturity fields from the project detail route. Internal cockpit and costing views are unavailable to clients. The administration-only project picklist exposes id, projectCode and title for assigning grants.

ProjectsController now filters its directory and gates project-specific routes with the new grant guard. Project creation is durable, creates a draft, and atomically records audit/outbox/idempotency; it creates no grant. Existing clone, dimensional closure and activity update commands remain unavailable over HTTP because their legacy implementations are not durable. They are not represented as completed business workflows. Other controllers still require their own project/audience/field-policy work; this batch does not close the all-controller boundary.

The web access register, role/reference screens, membership dialogs, project directory and cockpit errors display actual server state. Empty/denied project reads no longer substitute fixture projects or browser-local project records. The server role reference uses actual domain permission keys; it does not publish fixed approval ceilings or fabricated role demonstrations.
